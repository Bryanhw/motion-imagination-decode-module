# 测试与证据（testing）

> **"完工"的定义 = 有证据。** 没有证据的完成，一律视为未完成。
> 本文件回答一个问题：**这个项目里，"做完了"到底要拿出什么？**

---

## 1. 第一原则：数据来源决定结论效力

| 数据来源 | 可以用来做什么 | **绝对不可以**用来做什么 |
|---|---|---|
| `synth.py` / `mock` 源 | 验证**流程是否跑通**、字段是否合法、内存是否泄漏 | ❌ 评估算法性能 ❌ 对外报准确率 ❌ 写进任何汇报 |
| `replay`（录制/样本文件） | 验证**伪在线一致性**、滤波状态、滑窗正确性 | ❌ 作为真实准确率（数据本身仍是构造的） |
| **公开数据集**（BCI IV 2a/2b、OpenBMI） | ✅ **唯一可用于评估性能的数据** | —— |
| 真人采集（后期） | ✅ 系统可用性 | 需先过伦理审查 |

> **为什么强调**：在 `mock` 源上做交叉验证，**100% 是必然结果**（标签本来就是模型生成的）。
> 任何拿这个数字当成绩的行为，都属于学术诚信问题。

**红线**：MVP 阶段（至 10/27）**不对外报告任何准确率数字**。
真实数字须来自里程碑 ③ 的公开数据集评测。

## 2. 测试分层

| 层级 | 测什么 | 命令 | 通过标准 |
|---|---|---|---|
| 单元测试 | 缓冲、滤波、特征、分类器、稳定化各自独立正确 | `python -m pytest` | 全部通过 |
| 端到端自检 | 从数据源到输出全链路能跑并产出合法消息 | `python -m pytest`（含端到端用例） | 全部通过 |
| 伪在线回放 | 分块喂入与整段喂入结果是否一致（滤波状态） | `cli run --config configs/demo_replay.yaml` | 输出连续、无跳变 |
| 算力压测 | **不限速**下测量计算耗时分布 | `cli benchmark` | **p95 < 50 ms** |
| 长跑稳定性 | 连续 1 h 内存与耗时是否漂移 | 长跑脚本 | 无增长趋势 |
| 联调 | 游戏实际订阅到消息并驱动画面 | WebSocket | 动作与 `label` 一致 |

## 3. 必须覆盖的测试用例

### 3.1 缓冲
- [ ] 容量恒定（喂入超过容量后长度不变）
- [ ] 旧数据被正确覆盖，最新数据在最前/最后的位置约定一致
- [ ] 时间戳单调递增

### 3.2 因果滤波（**最关键**）
- [ ] **分块喂入 == 一次喂入**（数值误差在容差内）→ 证明跨 chunk 状态保持正确
- [ ] 块边界**无阶跃/跳变**
- [ ] 在线路径中**不存在** `filtfilt`

### 3.3 特征
- [ ] **CSP 路线**：`CSPExtractor.fit` 后 `transform` 维度 = `csp_components`（demo = 4 维）
- [ ] **空间滤波矩阵 W 随模型保存/加载**（`demo_csp.joblib`），`save → load` 后输出与训练时一致
- [ ] **通道顺序绑定**：CSP 的 W 行序与训练通道顺序一致，绝不重排（`C3, Cz, C4, CP3, CP4, P3, P4, Oz`）
- [ ] 对数变换后无 `NaN` / `Inf`
- [ ] 全零输入不崩溃、不产生 NaN
- [ ] 未训练（无 `features.model_path`）时在线链路给出明确报错/降级，不静默乱报

### 3.4 分类器
- [ ] 具备 `predict_proba`
- [ ] 输出长度恒为 2、和为 1
- [ ] **模型缺失/未训练 → 输出均匀概率**（进而走 `idle`）

### 3.5 决策稳定化
- [ ] 概率 EMA 平滑后是渐变而非突跳
- [ ] **连续 3 次一致**才切换类别
- [ ] 置信度低于门限 → 输出 `idle`
- [ ] 未训练时**恒输出 `idle`**，且 `label_id == -1`

### 3.6 伪迹
- [ ] 超阈值段被**标记**（`state` 变化或标记位）
- [ ] 数据**不被丢弃**（缓冲长度不变）
- [ ] 伪迹期间降级为 `idle`

### 3.7 输出契约
- [ ] 每个字段类型正确，数值是 JSON number 而非字符串
- [ ] `label_id == -1` ⟺ `label == "idle"`
- [ ] `probs` 长度恒为 2

## 4. 性能证据（必须来自自己写的代码）

`cli benchmark` 必须报出：

| 指标 | 含义 | 门槛 |
|---|---|---|
| p50 | 中位数计算耗时 | — |
| **p95** | 95 分位计算耗时 | **< 50 ms** |
| max | 最坏情况 | — |
| 端到端 | 窗口累积 + 计算 | ≤ 3 s |

并且**能解释延迟来源**：

```
T_response ≈ T_accumulate（滑窗 2.0 s）+ T_compute（数毫秒，本机实测 p95≈0.955 ms，A4）
# 对外分两个数讲：起步延迟 ≈2.1 s（A9 冷启动到首决策）；稳态延迟 <1 s（0.5 s 步长 + 单次计算）
# "~99.8% 在攒窗口"是单次决策构成的估算占比，不是端到端延迟；实测见 docs/evidence/W9_1027/01_延迟/
```

> 若有人提出"换个更强的模型来降低延迟"——**这是错误方向**，见
> `docs/research-BCI-Decoder.md` §2.1。
