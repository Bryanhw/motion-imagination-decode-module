## 1. 定位与边界

**做什么**：一个桌面弹球/接球小游戏，用键盘先做完整玩法，再把输入替换为解码消息流；现场演示"想象 → 挡板动"。

| ✅ 游戏端负责 | ❌ 游戏端不负责 |
|---|---|
| 玩法、碰撞、计分、动画、可重来 | 脑电采集、滤波、特征、分类（那是解码侧） |
| 订阅 WebSocket 消息并驱动画面（A7） | 判断"想象左手还是右手"（**它只消费消息，不需要懂脑电**） |
| 断线重连不崩溃（F5.3） | 训练模型、算准确率 |
| 把 `idle` 表现为"挡板不动"（F4.3） | 决定消息字段（字段已冻结） |
| 演示界面的可读性（投影仪可见） | 落盘 `jsonl` / 打印终端日志 |

> **架构含义**：游戏端是**可替换的消费者**。它坏了不影响解码链路成立；它不存在时，链路靠 `console` / `jsonl` 照样能验收。这条边界让 F4 与 F1 真正解耦，也就是"能并行开工"的前提。

## 4. 技术选型（含备选方案对比）

### 4.1 先拆开一个被混淆的问题 ⚠️

项目文档里"游戏端技术栈待定"其实混了**两个不同的问题**，这是措辞漂移的根因（复核 P3-1）：

| 问题 | 现状 | 结论 |
|---|---|---|
| **① 我们自己的 Demo 用什么？** | `MVP规格说明书` 附录A L600 已写 `python game\pong.py`；学习路线图 L30/L204/L250 指定 **Pygame**、责任人黄凯森 | **已定：Python + Pygame**（不是待定） |
| **② 企业未来客户端用什么？** | 若企业/其他团队做客户端，大概率用 **Unity** → 才需要 LSL4Unity vs WebSocket 的取舍 | **不在 MVP 范围**；MVP 只要保证 WebSocket 这条路通畅 |

→ **本文只解决 ①**。②的取舍依据见 `research-BCI-Decoder.md` §6（WebSocket 更轻、协议自研；LSL4Unity 生态偏旧且**许可证来源冲突未定论**）。

### 4.2 三个候选对比

| 候选 | 上手成本（4 名大一学生） | 与现有栈关系 | 对接方式 | 主要风险 | 结论 |
|---|---|---|---|---|---|
| **A. Python + Pygame** | 低。纯 Python，与解码器同语言、同虚拟环境 | **零新增技术栈**；`websockets` 已有 Python 客户端 | 直接用 `websockets` 客户端收 JSON | 画面表现力有限（演示级够了） | ✅ **采用** |
| B. Unity + LSL4Unity | 高。需装 Editor、学 C#、学 Unity 场景/生命周期 | 引入第二套工具链与版本管理 | Unity 侧收 LSL 流（或自写 C# WebSocket 客户端） | **LSL4Unity 主分支最后提交 2023-07-31，且许可证两路检索结论冲突（`NOASSERTION` vs MIT），采用前必须读 LICENSE 正文**；4 人团队工期不可控 | ❌ 不采用（Demo 阶段） |
| C. Web 前端（HTML/JS）+ WebSocket | 中。浏览器天然支持 WS，但 4 人对前端工程不熟 | 引入 Node/构建工具链 | 浏览器 `WebSocket` API | 与"本地单进程、无构建"的 MVP 取向相悖；无独显笔记本上浏览器渲染不占优 | ❌ 不采用 |

**为什么选 A（一句话）**：本项目唯一的性能红线是**解码耗时**，不是画面；Demo 需要的是"挡板跟手 + 投影仪看得清"，Pygame 双缓冲 60 FPS 完全够，而它把**新增技术栈降为 0**——4 个人只有 2 周，少一套工具链就是少一类翻车。

**选 A 放弃了什么**：放弃了 3D/粒子/物理引擎带来的观感上限（演示级→产品级），以及 Unity 生态现成的 UI 组件。**④ 阶段若企业要产品化界面，再评估 B。**

### 4.3 技术栈明细

| 组件 | 选择 | 说明 |
|---|---|---|
| 语言/运行时 | **Python 3.14.7** | 与解码器同一虚拟环境 `bci-decoder/.venv` |
| 游戏窗口/渲染 | **`pygame-ce`**（import 名仍为 `pygame`） | 双缓冲、60 FPS、无需独显；**上游 `pygame` 无 Python 3.14 wheel**（2026-10-16 实测），故用社区版 |
| WS 客户端 | **`websockets`**（asyncio，17.2） | ✅ **已装通并端到端验证**（2026-10-16；F5 关键风险已消除） |
| 配置 | 命令行参数 + 一个小的 `game/config_game.yaml`（可选） | 手感参数可调 |
| 不引入 | 物理引擎、GUI 框架（Qt/Tk）、Node/构建工具 | 明确排除，避免无谓依赖 |

## 5. 对接契约（WebSocket）

**服务地址**：`ws://127.0.0.1:8765`（`MVP规格说明书` L386 配置 `{kind: websocket, host: 127.0.0.1, port: 8765}`）。

### 5.1 服务端 → 游戏端（解码消息，字段已冻结，**不得增删**）

```json
{"t_data": 12.34, "t_wall": 12.51, "label": "left", "label_id": 0,
 "confidence": 0.83, "probs": [0.83, 0.17], "state": "running",
 "compute_ms": 1.7, "window_seconds": 2.0}
```

| 字段 | 游戏端怎么用 |
|---|---|
| `label` | `left` → 挡板左移；`right` → 右移；`idle` → **不动** |
| `label_id` | 可用作数组索引：`0`=left、`1`=right、`-1`=idle |
| `confidence` | 映射为挡板速度/加速倍率（**只影响手感，绝不影响方向**） |
| `probs` | 长度**恒定 2**（`[P(left), P(right)]`）；**不随 `idle` 变长**，索引可固定 |
| `state` | `running` / `stabilizing`；演示时用于界面状态显示，**不要用它改玩法** |
| `compute_ms` / `window_seconds` | 仅显示（"这一条算得多快"），不参与玩法 |
| `t_wall` | 端到端延迟统计（`t_wall` 减本机收包时刻），**可选** |

**解析纪律（写进代码注释）**：
- `label_id == -1` **当且仅当** `label == "idle"`——两者必须同时成立，**不要只信其一**；
- 数值一律是 JSON number，**不是字符串**（不要 `float(msg["confidence"])` 式的容错掩盖问题，坏了要能看见）；
- **不假设字段顺序**；
- `confidence` 在 `idle` 时表示"判定为不动"的置信度，**不代表方向**——用它调速会让"不动"变成"动得快"，是严重 bug。

### 5.2 游戏端 → 服务端（控制消息，可选）

| 消息 | MVP 是否需要 | 未实现时约定 |
|---|---|---|
| `{"cmd":"start"}` | 是（F5.2，P2 但建议做） | 收到即开始推送 |
| `{"cmd":"stop"}` | 是（F5.2） | 收到即停止推送 |
| `{"cmd":"calibrate","seconds":120}` | 否（④） | **忽略并记日志**，不报错、不断连 |
| `{"cmd":"load_subject","id":"sub01"}` | 否（④） | 同上 |

> **健壮性红线**：收到**无法识别的 `cmd`** 一律忽略并记日志，**绝不允许崩溃或断开连接**（`MVP规格说明书` §4.4）。这条对应 F5.3。

### 5.3 客户端行为要求

1. **断线重连**：指数退避重连（0.5s → 1s → 2s → 上限 5s），重连期间**画面继续跑、游戏不退出、键盘仍可玩**；
2. **不静默丢消息**：收到畸形消息 → 计数 + 终端警告，**不改变挡板状态**（宁可不动，符合视觉原则 1）；
3. **陈旧消息保护**：`t_data` 单调性检查；若消息明显过期（本地已收到更晚的），可丢弃并计数；
4. **超时保护**：连续 N 秒（建议 3 s，即约 6 条）没有新消息 → 界面显示"信号丢失"并让挡板**回到不动**（安全态），而不是保持最后一个方向。

## 6. 玩法与节奏约束 ⚠️ 本项目最容易翻车的地方

**硬事实**：窗口 2.0 s + 步长 0.5 s → 控制率只有 **每秒 2 条消息**（`research-BCI-Decoder.md` L295）。游戏玩法**必须为 2 Hz 的控制率设计**，而不是"设计好玩法再想办法提速"。

| 约束 | 落法 |
|---|---|
| **禁止快节奏玩法** | 不做连击/加速球/多球/需要 10 Hz 操作的机制。回合制节奏，允许"等一下才动" |
| **挡板速度匹配 2 Hz** | 单条指令驱动的位移量要**明显可见**（建议 ≥ 窗口宽度的 1/6），保证一次决策就看出效果 |
| **离散→连续的平滑** | 收到指令后做**插值动画**（如 0.5 s 内线性逼近目标位置），让画面跟手；**但插值不得改变指令语义**，尤其 `idle` 必须是"停在原地" |
| **`idle` 的安全含义** | 挡板停在原处。**绝不能**变成"随机左右"或"漂移"——这是红线 R-3 的界面体现 |
| **失球与回合** | 失球 → 记分 + 短暂停顿 + 重发球；提供 `R` 重开（F4.1"可重来"） |
| **手感可调** | `confidence` → 挡板速度倍率（建议 0.7x–1.3x），演示时可现场展示"专注度高就更跟手" |
| **窗口长度不得改** | 2.0 s 是冻结契约；改成 1.0 s 需**重新训练模型**（`MVP规格说明书` L342–343），不是改参数 |

**演示可读性**（F4.4）：窗口内固定显示 `label` + `confidence` + 当前 `state`；`idle` 与 `running` 用不同颜色区分（对齐 PRD 的终端视图约定）。

## 7. 外观与手感（承接 PRD 的 Look & Feel）

PRD 已确认设计基调（2026-10-15，团队确认不替换）：

**Design Vibe:** 干净 · 跟手 · 可复现 · 诚实

| PRD 视觉原则 | 游戏端的具体落法 |
|---|---|
| 1. **跟手优先**：让画面抽搐的实现都不算"完成" | 60 FPS 稳定；指令到达瞬间开始插值；**宁可不动，也不乱动** |

## 8. 目录与模块

> **位置已定案（2026-10-15）：`bci-decoder/game/`**。依据：`MVP规格说明书` 附录A 先 `cd bci-decoder` 再执行 `python game\pong.py`；且 `bci-decoder/` 已拍板为**本团队成果、计入进度**（`docs/Start项目落地评估.md` §5.1 方案 A）。下面的模块划分与位置无关。

```
game/
├── pong.py            # 入口：参数解析、主循环、组装（--input keyboard|ws|jsonl）
├── input_source.py    # 输入源抽象：KeyboardSource / WsSource / JsonlSource
├── ws_client.py       # WebSocket 客户端：连接、重连、解析、畸形消息计数
├── render.py          # 渲染：得分/状态/挡板/最近一条消息
├── config_game.yaml   # 手感参数（挡板速度、插值时长、配色）
└── tests/
    └── test_ws_protocol.py   # 协议解析单测（喂样例 JSON，不依赖真连接）
```

**设计要点**：
- **输入源可切换**是 F4.1/F4.2 的关键：键盘版与解码版**共用同一套玩法与渲染**，只换 `input_source`。这样"先做完整键盘玩法"不是额外工作，而是同一个程序的一个模式。
- `WsSource` 与 `JsonlSource` 实现**同一接口**（`next_command() -> label`），使降级路径（§10）不改玩法代码。
- `ws_client.py` 不依赖 Pygame，可**单独单测**（协议解析不靠人工点）。

## 10. 降级路径（时间不够时先砍什么）

对齐 `MVP规格说明书` §11.2 的三级降级：

| 级别 | 触发 | 游戏端的表现 |
|---|---|---|
| **A 级**（正常） | 一切正常 | WebSocket 实时驱动 |
| **B 级** | WebSocket 打不通 | **改读 `artifacts/decoder_output.jsonl`**（`--input jsonl`，轮询新增行）→ 演示从"实时"降为"准实时回放"，**玩法与界面完全不变** |
| **C 级** | 完全跑不通 / 时间不够 | 只演示**键盘版**（键 `←/→` 代替解码），配合终端输出讲清原理；进度如实通报，**不假装是脑控** |

> ⚠️ **C 级的诚实要求**：C 级演示时**必须明说这是键盘输入**。这正是 Design Vibe 里的"诚实"——虚报比降级更严重。
> 若最终改为本地 TCP 直连（PRD §F5 提到的另一条降级），`input_source.py` 再加一个 `TcpSource` 即可，接口不变。

|---|---|
| 协议解析 | 喂样例 JSON（正常 / `idle` / 字段顺序打乱 / 缺字段 / 数值被包成字符串）→ 断言行为：正常生效、畸形计数 +1 且**挡板状态不变** |
| `label_id` ⟺ `label` 一致性 | 构造矛盾样本（`label_id: -1` 但 `label: "left"`）→ 断言按`idle`处理并告警，不崩 |
| 断线重连 | 脚本起一个假 WS 服务端 → 杀掉 → 断言客户端重连且不退出（F5.3） |
| 陈旧/超时保护 | 喂过期 `t_data` → 断言丢弃；停止喂 3 s → 断言回到"不动" |

**人工验证（要留证据）**：

1. **键盘版完整可玩**：得分、反馈、可重来 → 录屏（F4.1）；
2. **解码版联调**：真实收到消息并驱动画面 → **录屏为证**（A7，注意是"画面真的动了"，不是"端口能连"）；
3. **`idle` 演示**：现场故意不动 → 挡板静止（F4.3）；
4. **1 h 长跑**：连续运行内存无增长、断线重连不崩（`大一学生学习路线图` W14）；
5. 证据归档到 `docs/evidence/W{n}_{日期}/`（`MVP规格说明书` §11.1）。

> 🚫 **红线（写进测试注释与演示脚本）**：**绝不**在界面、截图、答辩页里出现"准确率"数字。`mock`/`synth` 数据跑出来的任何性能数字**只用于工程自检**，对外报告准确率须等里程碑 ③ 的公开数据集评测。
