## 1. MVP 的边界：一句话与三条铁律

### 1.1 一句话定义（本文件的判据）

> **在 W9（10/27）之前，企业在一台普通笔记本上，按文档启动模块并接上游戏，3 分钟内完成一次"校准 → 试玩 → 出结果"的完整流程，且响应延迟有实测数字。**

### 1.2 三条铁律

| # | 铁律 | 含义 | 违反的后果 |
|---|---|---|---|
| 1 | **先降功能，不降节点** | 10/27 是课程硬节点，不可挪。时间不够就砍功能（第 11 节），绝不允许迟交 | 直接丢分，且影响后续 5 个里程碑 |
| 2 | **不用合成/模拟数据对外报准确率** | MVP 只报"链路通 + 延迟数字"；真实准确率留到 ③（11/10）用 `moabb` + BCI IV 2a 测 | 学术诚信风险，且 11/10 无法自圆 |
| 3 | **未训练/不可信时恒输出 `idle`** | 置信度不足、模型缺失、信号异常，一律输出"不动" | 游戏乱动，体验当场崩坏，演示失败 |

### 1.3 交付边界（谁负责什么）

| 分工 | 归属 | MVP 阶段说明 |
|---|---|---|
| 脑电采集硬件 | 企业 / 设备方 | MVP 用 `mock` / `replay` 数据源，**不接真实设备** |
| **在线解码模块** | **本项目** | 核心交付物（F1–F3、F5） |
| **横版闯关游戏 MI Pixel Run（platformer，主打）** | **本项目**（黄凯森） | MVP 必做（F4），先用**键盘**做完整玩法，再接解码消息（WS）驱动；弹球/格子版保留为备稿 |
| 真实被试采集与伦理 | 企业主导，我方配合 | MVP 阶段**不做**真人采集与伦理申请 |

## 2. 范围分界：MVP 做什么、不做什么

> 这是全文件最需要向评审与企业讲清的一节。**明确写"不做什么"，比罗列"做什么"更能体现工程成熟度。**

### 2.1 在 MVP 范围内（10/27 前必须交付）

| 编号 | 内容 | 验收要点 |
|---|---|---|
| **F1** | 在线解码链路（`mock` / `replay` 两种数据源可切换） | 两种源都能稳定输出，`replay` 能跟上类别切换 |
| **F2** | 输出接口（`console` + `jsonl`） | 字段与第 4 节契约**逐字段一致**，能落盘 |
| **F3** | 决策稳定化（EMA 平滑 + 连续 3 次一致性投票 + 置信度门限） | 含 `idle` 输出，不抖动 |
| **F4** | **脑控游戏 Demo（横版闯关 MI Pixel Run，platformer）** | 键盘可玩 → 换解码结果（WS）可玩；现场可演示"想象 → 角色动" |
| **F5** | WebSocket 输出打通 | 游戏实际订阅到消息并驱动画面（**第一次真正跑通**） |

### 2.2 明确不在 MVP 范围内（延后，且**不得挤占 F1–F5 的时间**）

| 内容 | 归属里程碑 | 为什么现在不做 |
|---|---|---|
| 真实数据准确率基线（`moabb` + BCI IV 2a） | ③ 11/10 | 需先有链路；MVP 只证明"通" |
| 伪在线回放一致性验证（与离线差 < 5%） | ③ 11/10 | 依赖真实数据集 |
| 模型训练产物保存 / 加载 | ③ 11/10 | 校准流程的前置，属中期 |
| 校准流程（引导页 + 2–3 min 采集） | ④ 12/01 | MVP 用预置演示模型 + `idle` 兜底即可 |
| LSL 真实设备接入 | ④ 12/01 | 设备型号未确认，接了也白接 |
| 黎曼几何 / 欧氏对齐（`pyRiemann`） | ④ 12/01 | 算法增强，非闭环必需 |
| 深度学习模型（EEGNet 等） | 本期不做 | 数据量不够，跨被试常打不过传统方法 |
| 多脑区融合消融实验 | ④ 可选项 | 企业点名的**探索性**方向，非 MVP 必需 |
| Docker / 一键部署 | ⑥ 12/15 | 交付包装，与闭环无关 |
| 4 类运动想象 | 本期不做 | 准确率撑不住，已冻结为 2 类 |

> **范围纪律**：MVP 期间**新增任何功能需求，一律视为里程碑 ③ 之后**。若企业口头提出新需求，记入《需求确认记录》的"待决策"栏，**不在 MVP 内实施**。

## 4. 接口契约 v1.0（冻结）

> **本契约在 MVP 期间不得再改。** 游戏与解码两条线并行开发，契约一变两边都对不上。
> 任何字段增删必须走第 9 节变更流程，并同步通知黄凯森（游戏）与王释贤（接口）。

### 4.1 输入：脑电数据流

| 项 | 约定 | 备注 |
|---|---|---|
| 数据格式 | 多通道时序，形状 `(n_channels, n_samples)` | 行=通道，列=时间 |
| 单位 | 微伏（µV） | 不做量纲转换 |
| 通道数 | 8 | 可配置，但 MVP 固定为 8 |
| 通道顺序 | `C3, Cz, C4, CP3, CP4, P3, P4, Oz` | **顺序即语义**，见下方警示 |
| 采样率 | 250 Hz | 可配置 |
| 数据块 | 建议 100 ms 一块（25 采样点） | `mock` / `replay` 沿用 |
| 时间戳 | 单调递增，单位秒（float） | 用于延迟测量 |
| 推荐接入 | LSL 流，名称可配置 | **MVP 不接真实设备** |

> ⚠️ **通道顺序是本项目最容易出错、最难排查的问题**。
> 顺序错了，C3/C4 的侧向性完全颠倒，模型会**稳定地输出相反结果**（看起来"很准"，其实全反）。
> **MVP 用 `mock`/`replay` 时，通道顺序由我们自己定义，必须与配置里的 `ch_names` 严格一致。**
> 后期接真实设备时，此顺序必须由企业**书面确认**（见《需求确认记录》待确认项 Q1）。

### 4.2 输出：解码结果消息（JSON，UTF-8，每行一条）

```json
{
  "t_data": 12.345,
  "t_wall": 8412.551,
  "label": "left",
  "label_id": 0,
  "confidence": 0.83,
  "probs": [0.83, 0.17],
  "state": "running",
  "compute_ms": 1.2,
  "window_seconds": 2.0
}
```

| 字段 | 类型 | 单位 | 必填 | 取值范围 | 含义 |
|---|---|---|---|---|---|
| `t_data` | float | s | 是 | 单调递增 | 本窗口最后一个采样点的时间戳 |
| `t_wall` | float | s | 是 | 单调递增 | 输出时刻的本地时钟（用于端到端延迟统计） |
| `label` | string | — | 是 | `left` / `right` / `idle` | 解码结果 |
| `label_id` | int | — | 是 | `0` / `1` / `-1` | 类别索引；`idle` 恒为 `-1` |
| `confidence` | float | — | 是 | `0.0`–`1.0` | 当前输出类别的置信度 |
| `probs` | float[] | — | 是 | 长度 2，和为 1 | `[P(left), P(right)]`；`idle` 时保留上一次或输出先验 |
| `state` | string | — | 是 | `running` / `stabilizing` | 决策稳定化状态 |
| `compute_ms` | float | ms | 是 | ≥ 0 | 本次推理耗时（用于延迟分解） |
| `window_seconds` | float | s | 是 | = 2.0（MVP） | 本窗口长度 |

**字段语义补充（约定清楚，避免歧义）**：

- `label_id` 为 `-1` 当且仅当 `label == "idle"`；二者**必须同时成立**，不得只改其一。
- `probs` 恒定长度 2（对应 `left` / `right`），**不随 `idle` 改变长度**；游戏侧数组索引固定。
- `confidence` 是**当前输出类别**的置信度；当 `label == "idle"` 时，`confidence` 表示"判定为不动"的置信度。
- 数值一律为 JSON number，**不使用字符串包装数字**（避免游戏侧解析歧义）。

### 4.5 状态机

```
   ┌────────┐  start   ┌──────────────┐  校准完成   ┌─────────┐
   │  IDLE  │─────────▶│ CALIBRATING  │────────────▶│ RUNNING │
   └────────┘          └──────────────┘             └────┬────┘
        ▲                                               │
        │                  stop / 信号质量持续异常       │
        └───────────────────────────────────────────────┘
                              │
                              ▼
                        ┌───────────┐
                        │  ERROR    │  设备断开 / 数据超时
                        └───────────┘
```

| 状态 | 行为 | 对外输出 | MVP 范围 |
|---|---|---|---|
| `IDLE` | 不推理 | 不发消息 | **是** |
| `CALIBRATING` | 采集校准数据、训练/微调模型 | 只发进度 | 否（④），MVP 直接进入 `RUNNING` |
| `RUNNING` | 正常解码 | 发 `label` / `idle` | **是** |
| `ERROR` | 停止推理、告警 | 发错误状态 | 部分（仅"模型缺失 / 数据超时"两条路径） |

> **MVP 简化说明**：MVP 不实现 `CALIBRATING`，启动即 `RUNNING`，使用预置演示模型；
> 但**必须实现"模型缺失 → `idle`"与"数据超时 → `ERROR`"两条兜底路径**（F3.4）。

### 5.3 为什么滑窗冻结在 2.0 s（全项目最重要的一个决策）

端到端响应时间可近似分解为：

```
T_response ≈ T_accumulate + T_compute
             └─ 滑窗长度 ─┘   └─ 单次计算 ─┘
```

| 项 | 量级（本团队链路实测·合成数据自检） | 占比 |
|---|---|---|
| `T_compute` p50 | 1.5 ms | — |
| `T_compute` p95 | 2.1 ms | **0.10%** |
| `T_accumulate` | 2000 ms | **99.90%** |
| **合计 p95** | **≈ 2002 ms** | 100% |

> ⚠️ 上表数字来自**我们自己的解码链路（`bci-decoder/`）+ 合成数据自检**，仅用于说明量级与技术可行，
> **不是算法性能指标**。真实设备 / 回放数据上的数字须用 `cli benchmark` 实测并留档（F6.2）。

**由此得到的最重要结论**：

> **延迟瓶颈不在算法，而在窗口长度。**
> 把 LDA 换成深度网络、或买更好的显卡，对端到端延迟**几乎没有帮助**；
> 真正有效的手段是**缩短窗口**——但窗口越短，可用信息越少，准确率越低。

**游戏节奏 → 窗口长度对照（冻结依据）**：

| 游戏类型 | 可接受响应 | 建议窗口 | 后果 |
|---|---|---|---|
| 回合制 / 迷宫 / **弹球** | 2–3 s | **2.0 s（MVP 采用）** | 准确率优先 |
| 弹球（快节奏）/ 赛车 | 1–1.5 s | 1.0 s | **需重新训练模型**，非改参数即可 |
| 实时动作（射击/格斗） | < 0.5 s | — | 运动想象范式**不适合**，请勿提此需求 |

> **给企业的建议**：不要在需求上既要"高准确率"又要"极低延迟"——这在物理上冲突。
> 正确做法是**先定游戏节奏，再倒推窗口长度，最后在窗口内优化准确率**。

## 7. MVP 技术方案：选什么、为什么、放弃了什么

### 7.1 主链路

```
原始 EEG ─▶ 因果滤波 ─▶ CAR重参考 ─▶ 伪迹标记 ─▶ 环形缓冲
                                                     │
                                          滑窗(2s/步长0.5s)
                                                     ▼
                                     CSP 特征 ─▶ LDA ─▶ 决策稳定化 ─▶ 输出
                                                                    ├─ console
                                                                    ├─ jsonl
                                                                     └─ websocket ─▶ 横版闯关游戏（MI Pixel Run）
```

### 7.2 关键选型与取舍

| 环节 | MVP 选择 | 为什么 | 放弃了什么 |
|---|---|---|---|
| 工频 | 50 Hz 陷波（IIR, Q=30），**因果带状态** | 中国工频 | — |
| 带通 | 8–30 Hz（mu + beta） | 运动想象主频段 | 更细的子带（FBCSP），取 ④ |
| 重参考 | CAR | 无状态、简单有效 | 拉普拉斯等空间滤波 |
| 伪迹 | 峰峰值阈值，**只标记不丢弃** | 丢弃会造成输出中断，游戏体验更差；标记后降级为 `idle` 更符合直觉 | ICA / ASR 在线实现，取 ④ |
| 特征 | **CSP + log-方差**（4 维） | 空间滤波判别力强；在线仅一次矩阵乘，实测 `compute p95≈0.9 ms`（≪50 ms 预算） | 频带功率（旧默认）· 协方差 + 黎曼几何（② 阶段主力） |
| 分类器 | **LDA** | 小数据、低延迟的强基线 | 深度模型（数据量不够） |
| 后处理 | **EMA + 3 次投票 + 置信度门限** | **宁可迟钝，不可抖动** | 更激进的实时响应 |

### 7.3 为什么不上深度学习（写给答辩）

1. **数据量不够**：单个被试往往只有几百个 trial，深度模型容易过拟合；
2. **跨被试更差**：EEGNet 等在小数据跨被试上**经常打不过 CSP + LDA / 黎曼**；
3. **对延迟没帮助**：计算只占端到端的 **0.1%**，换模型不会让游戏更快；
4. **正确顺序**：先用传统方法建立**可信基线**，再谈是否值得上深度。
