# 脑控游戏 · 在线解码模块设计说明

> 项目：非侵入式脑机接口运动想象在线解码（翔宇医疗校企合作）
> 定位：**交付一个可独立运行、可被游戏直接调用的在线解码模块**
> 版本：v1.0 · 配套可运行工程骨架 `bci-decoder/`
> 文档关系：主文件为 `docs/项目计划书.md`（要做什么）；**本说明是工程交付说明（怎么实现、接口是什么）**；`docs/详细技术路线.md` 是技术论证附录（为什么这么做）。
> **接口契约的冻结版本以 `docs/MVP规格说明书.md` 第 4 节为准**；本文第 4 节为其工程侧展开，如两者不一致，以《MVP规格说明书》为准。

## 1. 交付边界：什么归我们，什么不归我们

这一节必须先写清楚，否则项目很容易做成"半个游戏 + 半个算法"的四不像。

| 分工 | 归属 | 说明 |
|---|---|---|
| 脑电采集硬件 | 企业 / 设备方 | 我们只对接其数据流（优先 LSL） |
| **在线解码模块** | **本项目** | **核心交付物** |
| 游戏画面、玩法、UI | 游戏团队 | 我们只提供标准输出接口 |
| 游戏与解码的联调 | 双方 | 以本文第 4 节的接口契约为准 |
| 真实被试采集与伦理 | 企业主导，我们配合 | 涉人数据必须走伦理审查 |

**我们交付的"产品"就是一段消息流**：

```
{"label": "left", "confidence": 0.83, "probs": [0.83, 0.17], "t_data": 12.345, ...}
```

游戏拿到它就能驱动角色——这是衡量模块成败的唯一标准。

## 2. 系统架构

```
┌─────────────────────────────────────────────────────────┐
│                     bci-decoder 进程                     │
│                                                          │
│  数据源层        缓冲层           处理流水线        输出层  │
│  ┌──────┐      ┌────────┐      ┌──────────┐    ┌───────┐ │
│  │ mock │      │ 环形   │      │ 因果滤波 │    │console│ │
│  │replay│─────▶│ 缓冲   │─────▶│ CAR 重参考│───▶│ jsonl │ │
│  │ lsl  │      │(固定容量)│      │ 伪迹检测 │    │  ws   │ │
│  └──────┘      └────────┘      └────┬─────┘    └───────┘ │
│                                     ▼                    │
│                          ┌──────────────────┐            │
│                          │ 滑窗触发决策      │            │
│                          │ 特征→分类→稳定化  │            │
│                          └──────────────────┘            │
└─────────────────────────────────────────────────────────┘
```

### 分层原则

1. **数据源可替换**：只要实现 `Source.stream()`，就能接入任意设备。这是"交付即插即用"的关键。
2. **流水线各环节独立可测**：预处理、特征、分类、后处理都能单独单元测试，便于定位问题。
3. **输出多通道**：同一次解码可同时送终端（调试）、落盘（数据资产）、WebSocket（游戏）。
4. **配置驱动**：所有参数集中在 YAML，交付时企业只改一个文件。

## 3. 时间预算：在线解码的真正难点

这是本项目最需要向企业讲清楚的一件事。

### 3.1 为什么"离线能跑"不等于"在线能跑"

| 差异点 | 离线 | 在线 |
|---|---|---|
| 滤波 | 零相位 `filtfilt`，可看全数据 | **必须因果**，只能看过去 |
| 数据 | 完整 trial，可反复分析 | 分块到达，只有历史窗口 |
| 延迟 | 无约束 | 硬约束，超时即失效 |
| 稳定性 | 只看平均准确率 | 还看**抖动**与**误触发** |

**因果滤波是最大的隐形陷阱**：离线用零相位滤波，在线换成因果滤波后，
相位延迟会改变特征分布，导致在线准确率明显低于离线。必须从一开始就用因果滤波做实验。

### 3.2 延迟分解模型

端到端响应时间可近似分解为：

```
T_response ≈ T_accumulate + T_compute
             └─ 滑窗长度 ─┘   └─ 单次计算 ─┘
```

**实测数据**（本团队链路，250Hz，8 通道，2s 窗口，bandpower+LDA，**合成数据自检**）：

| 项 | 本团队链路实测 | 说明 |
|---|---|---|
| T_compute p50 | 1.5 ms | 滤波 + Welch + 特征 + LDA + 平滑 |
| T_compute p95 | 2.1 ms | 可忽略不计 |
| T_compute max | 4.7 ms | 可忽略不计 |
| T_accumulate | 2000 ms | **占据 99.9%** |
| **合计 p95** | **≈ 2002 ms** | |

### 3.3 由此得到的最重要结论

> **延迟瓶颈不在算法，而在窗口长度。**
> 优化模型（改成深度网络、上 GPU）对端到端延迟几乎没有帮助；
> 真正有效的手段是**缩短窗口**——但窗口越短，可用信息越少，准确率越低。

因此，**"窗口长度"是本项目最核心的工程决策**，必须与游戏团队共同确定：

| 游戏类型 | 可接受响应 | 建议窗口 | 后果 |
|---|---|---|---|
| 回合制 / 迷宫 | 2–3 s | 2.0 s | 准确率优先 |
| 弹球 / 赛车 | 1–1.5 s | 1.0 s | 需重新训练模型 |
| 实时动作 | < 0.5 s | — | 运动想象范式**不适合** |

**给企业的建议**：不要在需求上既要"高准确率"又要"极低延迟"，这在物理上冲突。
正确做法是先定游戏节奏，再倒推窗口长度，最后在窗口内优化准确率。

### 3.4 时间预算红线（工程验收标准）

| 指标 | 目标 | 依据 |
|---|---|---|
| 单次计算耗时 p95 | < 50 ms | 留足余量，保证低配设备可用 |
| 采集到决策的调度抖动 | < 10 ms | 避免线程阻塞 |
| 长时间运行 | 连续 1 h 无内存增长 | 环形缓冲保证内存恒定 |

## 4. 接口契约（游戏团队对接依据）

### 4.1 输入：脑电数据流

| 项 | 约定 |
|---|---|
| 数据格式 | 多通道时序，形状 `(n_channels, n_samples)` |
| 单位 | 微伏（µV） |
| 推荐通道 | `C3, Cz, C4, CP3, CP4, P3, P4, Oz`（运动区 + 枕叶，为多脑区融合预留） |
| 采样率 | 250 Hz（可配置） |
| 推荐接入 | LSL 流，名称可配置 |
| 数据块 | 建议 100 ms 一块 |

### 4.2 输出：解码结果消息

```json
{
  "t_data": 12.345,
  "t_wall": 8412.551,
  "label": "left",
  "label_id": 0,
  "confidence": 0.83,
  "probs": [0.83, 0.17],
  "state": "running",
  "compute_ms": 1.2,
  "window_seconds": 2.0
}
```

| 字段 | 含义 | 游戏侧建议用法 |
|---|---|---|
| `label` | 解码结果：`left` / `right` / `idle` | 直接映射为游戏动作 |
| `label_id` | 类别索引，`idle` 为 -1 | 数组索引 |
| `confidence` | 置信度 0–1 | 做视觉强度、难度自适应 |
| `probs` | 各类别概率 | 做连续控制（如速度） |
| `state` | `running` / `stabilizing` | `stabilizing` 时游戏可降低响应 |
| `t_data` | 数据时间戳 | 用于延迟测量与日志对齐 |
| `t_wall` | 输出本地时钟 | 用于端到端延迟统计 |

### 4.3 控制：运行状态命令（建议后续扩展）

建议游戏侧通过同一连接发送控制消息：

```json
{"cmd": "start"}          // 开始解码
{"cmd": "stop"}           // 暂停（如局间休息）
{"cmd": "calibrate", "seconds": 120}   // 进入校准
{"cmd": "load_subject", "id": "sub01"} // 切换被试模型
```

## 5. 状态机

在线模块必须显式管理状态，否则容易出现"用未校准模型驱动游戏"这类事故。

```
   ┌────────┐  start   ┌──────────────┐  校准完成   ┌─────────┐
   │  IDLE  │─────────▶│ CALIBRATING  │────────────▶│ RUNNING │
   └────────┘          └──────────────┘             └────┬────┘
        ▲                                               │
        │                  stop / 信号质量持续异常       │
        └───────────────────────────────────────────────┘
                              │
                              ▼
                        ┌───────────┐
                        │  ERROR    │  设备断开 / 数据超时
                        └───────────┘
```

| 状态 | 行为 | 输出 |
|---|---|---|
| `IDLE` | 不推理 | 不发消息 |
| `CALIBRATING` | 采集校准数据、训练/微调模型 | 只发进度 |
| `RUNNING` | 正常解码 | 发 `label`/`idle` |
| `ERROR` | 停止推理、告警 | 发错误状态 |

## 6. 预处理与特征的技术选择

### 6.1 预处理链（在线版）

| 步骤 | 方法 | 在线注意点 |
|---|---|---|
| 工频 | 50 Hz 陷波（IIR, Q=30） | 因果、带状态 |
| 带通 | 8–30 Hz（mu + beta） | 因果、带状态 |
| 重参考 | 共平均参考 CAR | 无状态，简单有效 |
| 伪迹检测 | 峰峰值阈值 | 只标记不丢弃，由上层决定降级为 idle |

**为什么不丢弃含伪迹的窗口**：丢弃会造成输出中断，游戏端体验反而更差。
更好的是**标记并输出 idle**，游戏表现为"这次没识别到"，符合用户直觉。

### 6.2 特征路线对比

| 特征 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **频带功率（当前默认）** | 快、可解释、数据需求低 | 未利用空间信息 | **第一版主力** |
| 协方差 + 黎曼几何 | 跨被试强、对噪声可控 | 计算稍高 | 第二阶段主力 |
| CSP / FBCSP | 经典、有效 | 需正则化、被试相关 | 基线对比用 |
| 深度特征 | 上限高 | 数据需求大、跨被试差 | 后期探索 |

### 6.3 多脑区融合（企业点名方向）

骨架已按 `C3, Cz, C4, CP3, CP4, P3, P4, Oz` 布置通道，天然包含：
- **运动区**（C3/Cz/C4/CP3/CP4）：运动想象主战场
- **枕叶**（Oz/P3/P4）：alpha 节律与注意状态
- **前额叶**（需额外加 F3/F4/Fz）：认知负荷、注意

融合方法（按复杂度递增）：
1. 特征级拼接（最简单，先做这个建立基线）
2. 分区独立分类 + 决策融合
3. 多分支网络 + 区域注意力（研究向）

**必须做消融实验**：单区 vs 多区。没有增益也是有效结论——它能避免后续投入浪费。

## 7. 测试策略（保证交付质量）

| 层级 | 内容 | 工具 |
|---|---|---|
| 单元测试 | 缓冲覆盖/时间戳、滤波状态连续性、特征维度、分类器接口、稳定化逻辑 | pytest |
| 端到端自检 | mock 源跑通全链路并产出结果 | pytest + mock 源 |
| **伪在线回放** | 用真实离线数据分块重放，检验滤波状态与滑窗 | replay 源 |
| 算力压测 | 不限速测量计算耗时分布 | `cli benchmark` |
| 稳定性测试 | 连续运行 1 h，观察内存与耗时漂移 | 长跑脚本 |
| 真实联调 | 接真实设备 + 游戏客户端 | LSL |

**本团队链路的验证结果（合成数据自检，2026-10-15 核实）**：

- 单元测试 **17/17 通过**（2026-10-16；含新增 WebSocket 契约测试 2 个）
- 计算耗时 p50 ≈ 1.5 ms，p95 ≈ 2.1 ms，max ≈ 4.7 ms（合成数据，**非算法性能**）
- mock 源与 replay 源均能正确跟踪类别切换
- 端到端延迟模型成立（瓶颈为窗口长度）

> **口径（2026-10-15 拍板）**：`bci-decoder/` 是**本团队成果**、计入项目进度（详见 `docs/Start项目落地评估.md` §5.1 方案 A）。
> 但以上数字来自**合成数据**，**不能作为算法性能指标**；真实数字须在里程碑 ③ 用公开数据集得到。

**已有链路中未跑通、仍需实现的功能**：

| 模块 | 状态 | 说明 |
|---|---|---|
| WebSocket 输出 | ✅ **已跑通**（2026-10-16） | `websockets 17.2` 装通并端到端验证（`--outputs websocket` ← 客户端收消息、9 字段契约逐条一致） |

## 9. 风险清单

| 风险 | 后果 | 对策 |
|---|---|---|
| 在线直接套用离线零相位滤波 | 在线准确率暴跌 | 从第一天就用因果滤波做实验 |
| 窗口长度与游戏节奏不匹配 | 游戏"不跟手" | 先定游戏节奏，再倒推窗口 |
| 无模型时输出随机指令 | 游戏乱动、体验崩坏 | 置信度门限 → 未训练时恒 idle（已实现） |
| 只看准确率不看抖动 | 用户挫败 | 稳定化三重机制（已实现） |
| 不做伪在线验证 | 接设备才发现问题 | replay 回放列为必做测试 |
| 拿合成数据当成绩 | 学术风险 | `synth.py` 已明确标注仅用于自检 |
| 涉人数据无伦理审查 | 合规风险 | 真实采集前完成审查与知情同意 |

## 附录 A：如何运行当前骨架

```powershell
cd bci-decoder

.venv\Scripts\activate
pip install -r requirements.txt

python -m pytest                                          # 单元测试
python scripts/bootstrap_demo.py --config configs/default.yaml   # 训练演示模型
python -m bci_decoder.cli run --config configs/demo_online.yaml --chunks 200
python -m bci_decoder.cli benchmark --config configs/demo_online.yaml --chunks 600
```

## 附录 B：切换到真实设备

1. 确认设备能发布 LSL 流（大多数采集软件都有该选项）
2. 安装 `pip install pylsl`
3. 修改配置：

```yaml
source:
  kind: lsl
  stream_name: "你的设备流名称"
  ch_names: [与设备实际通道顺序一致的通道名]   # 顺序必须完全一致
  sfreq: 250.0
```

4. 先用 `console` 输出观察 1 分钟，确认信号质量与时间戳正常
5. 再切到 `websocket` 与游戏联调

> **通道顺序必须与设备一致**，这是最容易出错也最难排查的问题——顺序错了，
> C3/C4 的侧向性完全颠倒，模型会稳定地输出相反结果。
