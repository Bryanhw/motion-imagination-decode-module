## 0. 回归参数（与 demo_weak 完全一致）

`configs/demo_online.yaml`、`configs/demo_replay_switch.yaml` 头注释 + `ood:` 块（插在 postprocess 后）：

```yaml

  enabled: true         # 与 demo_weak 同参启用（灰度扩展）
  method: mahalanobis
  chi2_quantile: 0.99
  score_scale: 1.0
  strength_floor_enabled: true
```

> `artifacts/ood.joblib` 由 **demo_weak（弱信号域，α≈15µV）** 训练标定（τ_final=13.2767，cf. D3）。

## 2. 变化点逐一核对（replay 的 +7 idle）

逐条时间轴比对（见附件 log）：新增 idle 全部落在**左右类别切换边缘及其相邻 1–2 个窗**
（如 5.5–7.0 s 左→右切换、14.5 s、22.5 s 右→左切换附近），属 OOD 把「过渡 / 次置信窗」判为域外 → `idle` 的**保守行为**；
左右主体信号仍保留（left 16 / right 11），**左↔右交替节律仍清晰可辨，无持续全 idle**。
符合红线「未把握 → 宁可 idle 也不错判」。

**如实注意事项**（不掩盖，供组长复核）：

1. **probs 与 label 解耦为既有设计**（基线日志同样可见 `label=idle 但 probs=[1.00 0.00]`）：
   OOD 命中把当前窗概率置均匀 [0.5,0.5]，稳定器 vote/EMA 在**切换边缘的 1–2 窗内仍可能短暂残留 left/right 标签**，随后收敛到 idle。
   属防抖惯性，非 OOD 机制新增缺陷。
2. **训练域 / 使用域差异**：`ood.joblib` 由弱信号域（demo_weak）标定，而回放样本功率更高、切换处统计量更易越界，
   因此 replay 下比 mock 观察到了更多边缘转 idle——这正是拍板**第 3 项「版本绑定 M2 后再议」**要跟踪的场景（正式版应对
   使用域重训 ood 或按域绑定模型）。MVP 阶段按拍板**同参启用、不擅调阈值**。
3. **延迟预算**：开启 OOD 后 compute p95 增量 ≈ 0.07 ms（replay）且与机器/时刻相关（组长本机 demo_weak p95≈0.41 ms，
   本机实测见附 log），**均 ≪ +1 ms 预算**。
