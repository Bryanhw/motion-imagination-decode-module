# 脑控游戏（BCI Game）方向 · 专题建议

> 承接《非侵入式脑机接口 · 运动想象在线解码模块 —— 校企合作项目初步思路与实施规划 v1.0》
> 适用：智能医学工程专业大一团队 / 翔宇医疗合作项目
> 定位：把"运动想象在线解码"落到一个**能演示、能收集数据、能打动企业**的具体产品形态上

---

## 1. 战略判断：为什么"主攻脑控游戏"是对的

| 对比维度 | 脑控轮椅 | **脑控游戏** |
|---|---|---|
| 容错要求 | 极严（安全责任） | 宽松（错了重来） |
| 决策窗口 | 越短越好 | 可以设计成 1–3 s |
| 精度门槛 | 高（>90% 才敢用） | 中（70% 就能"玩起来"） |
| 数据回流 | 少 | **多（游戏中持续产生标注数据）** |
| 演示效果 | 风险高、难展示 | 视觉冲击强、易做 Demo |
| 康复契合度 | 一般 | **极高（游戏化康复）** |

**结论**：脑控游戏不是"降低难度的妥协"，而是**最合理的技术验证载体与数据引擎**——先用游戏把"在线解码闭环"跑稳、把数据攒起来，再把同一套解码模块复用到轮椅场景。这与企业"最终形成可调用的在线解码模块"的目标完全一致。

> **一句话策略**：用游戏打磨在线解码模块，用康复场景放大企业价值。

## 2. 第一原则：脑控游戏的成败，80% 在游戏设计，不在算法精度

这是新手团队最容易搞反的地方。现实约束必须先接受：

### 2.1 必须接受的三个现实

1. **BCI Illiteracy（脑机盲）**：约 15–30% 的被试对运动想象范式不敏感，怎么练都分不出来。这是范式问题，不是你的算法差。
2. **延迟是物理存在的**：滑窗 2–4 s + 推理，意味着"指令"有秒级延迟，游戏节奏必须为它让步。
3. **运动想象很累**：高强度 MI 持续 10 分钟就会明显疲劳，游戏单局时长要短。

### 2.2 由此推出的设计铁律

- **铁律一（少指令）**：第一版只做 **2 类**（想象左手 / 想象右手），或 **3 类**（+ 静息）。不要一上来 4 类。
- **铁律二（慢节奏）**：游戏节奏必须匹配秒级决策窗口。回合制、节奏舒缓的玩法 > 高频实时操作。
- **铁律三（强反馈）**：用户必须能**看到自己的脑电在被响应**，否则无法学会调节。反馈延迟要短、要连续。
- **铁律四（有静息态）**：必须有"什么都不做"的类别/阈值机制，否则**误触发**会毁掉体验。
- **铁律五（可重来）**：单次判断错误不能导致游戏失败或严重后果。
- **铁律六（有备选）**：为分不出 MI 的用户准备退路——降为 1 类（"专注/放松"）、换范式（SSVEP）或纯辅助模式。

## 3. 玩法设计建议

### 3.1 推荐的游戏类型（按实现难度排序）

| 游戏 | 映射方式 | 难度 | 说明 |
|---|---|---|---|
| **脑控弹球 / 打砖块** | 左手/右手 → 挡板左右移 | ★ | 最适合第一个 Demo，逻辑简单、反馈直观 |
| **脑控赛车 / 飞船** | 左/右想象 → 转向；静息 → 减速 | ★★ | 视觉冲击好，适合演示 |
| **脑控贪吃蛇 / 迷宫** | 二选一转向 | ★★ | 回合决策，天然适配秒级延迟 |
| **脑控跳一跳 / 节奏游戏** | 想象 → 蓄力跳跃 | ★★ | 有"蓄力"机制可掩盖延迟 |
| **康复训练游戏（企业最看重）** | 想象患侧手 → 驱动虚拟手抓取 | ★★★ | 对齐翔宇康复场景，可做临床叙事 |
| **脑控宠物养成 / 环境互动** | 多动作 + 静息 | ★★★ | 长周期、可收集数据，趣味性强 |
| **脑控音乐 / 绘画** | 想象 → 生成音/色 | ★★ | 偏神经反馈与放松训练，适合康复情绪干预 |
| **脑控虚拟轮椅 / 角色行走** | 想象 → 前进/转向 | ★★★★ | 本质是轮椅的"减风险版"预演 |

### 3.2 明确**不推荐**的类型

- FPS / 格斗 / 需要高频精确瞄准的游戏（延迟与精度都无法满足）
- 需要 4 类以上连续指令的游戏（第一版精度撑不住）
- 失败惩罚重、无法重来的设计

### 3.3 一个具体的第一个 Demo 设计（建议直接照做）

**《脑控弹球（Brain Pong）》**

- **输入**：2 类运动想象（左手 / 右手）
- **映射**：左手想象 → 挡板左移；右手想象 → 挡板右移；连续输出取平滑后的方向
- **决策**：滑窗 2 s，步长 0.25 s，输出方向 + 置信度
- **反馈**：挡板移动 + 屏幕边缘光效随置信度增强 + 可选音效
- **容错**：球掉落 → 分数清零但可无限重来
- **附加**：屏幕上实时显示"当前判定：左 / 右 / 静息"和置信度条，既方便用户学习，也方便你们调试
- **成功标准**：能连续玩 3 分钟、不崩、用户有"我在控制它"的主观感受

## 4. 控制映射：从"开关"到"连续"

| 映射类型 | 做法 | 适用阶段 | 难度 |
|---|---|---|---|
| **离散二值（开关）** | 想象 → 触发一个动作 | 第一版 | ★ |
| **离散多类** | 左/右/静息 → 三种动作 | 第二版 | ★★ |
| **比例控制** | 分类置信度/μ 功率衰减程度 → 速度大小 | 进阶 | ★★★ |
| **状态机导航** | MI 只负责"选方向"，游戏自动执行移动 | 实用推荐 | ★★ |
| **混合范式** | MI + SSVEP + 眼动 | 研究向 | ★★★★ |

**务实建议**：
- **第一版坚决用离散二值 + 静息**；
- 引入**置信度门限 + 输出平滑**（例如最近 5 次决策投票、连续 3 次同向才切换），能显著提升"稳定感"——用户主观体验提升往往比准确率提升 3 个点更明显；
- **宁可迟钝，不可抖动**：游戏里频繁误切方向比偶尔慢半拍更让人挫败。

## 5. 交互与体验设计（决定游戏"好不好玩"的地方）

### 5.1 四类反馈缺一不可

1. **即时反馈**：每次决策后 200 ms 内给出可视响应；
2. **连续反馈（神经反馈）**：用进度条/光晕实时显示"你的想象强度"，帮助用户找到感觉；
3. **结果反馈**：得分、进度、成功动画；
4. **学习反馈**：局间给出"本局准确率/反应时间"，让用户越玩越会。

### 5.2 校准流程（必须设计进游戏）

```
进入游戏 → 引导页（30s 说明） → 校准采集（2–3 min，采集 20–30 个 trial/类）
→ 训练/加载分类器 → 试玩 1 局 → 若准确率过低则提示重校准或降难度
```

- 校准阶段要**给足引导**（屏幕上出现"想象左手"提示 + 倒计时）；
- 支持**在线自适应微调**（用游戏中的数据进行轻量更新），抵抗跨次漂移；
- 保存每个用户的校准模型，下次可用**迁移/微调**减少校准时间——这正是前面规划的"跨被试迁移"要解决的，**游戏恰好成为最好的验证场**。

### 5.3 疲劳与安全

- 单局 2–4 分钟，中间强制休息提示；
- 检测到信号质量变差（大量伪迹）时提示用户放松、眨眼、调整电极；
- 康复场景（患者）必须有人监护，且需通过伦理审查与知情同意。

## 6. 技术架构与选型

### 6.1 总体架构

```
[EEG 采集设备]
      │  LSL（Lab Streaming Layer）
      ▼
[在线解码模块 · Python]
  环形缓冲 → 因果滤波 → 伪迹检测 → 滑窗特征 → 分类器 → 平滑/门限
      │  WebSocket / OSC / UDP / gRPC
      ▼
[游戏客户端 · Unity / Godot / Web / pygame]
      │
      ▼
[画面 + 音效 + 记录模块（trial、标签、时间戳）]
```

**关键设计点**：
- **解码与游戏解耦**：解码模块独立进程，通过标准协议输出"意图 + 置信度 + 时间戳"。这样同一模块可随时换成轮椅客户端——**这就是企业要的"可调用在线解码模块"**。
- **时间戳贯穿全链路**：LSL 天然带时间戳，游戏侧记录 trial 起始时刻，便于事后对齐分析与计算真实延迟。
- **记录一切**：原始数据、预测、置信度、时间戳、用户操作，全部落盘 → 这是你们后续做迁移学习/自适应的数据资产。

### 6.2 通信协议选型

| 协议 | 延迟 | 适用 | 建议 |
|---|---|---|---|
| **WebSocket** | 低 | Web 游戏、跨语言 | 首选，易调试 |
| **OSC** | 低 | Unity / 音乐类 | Unity 生态友好 |
| **UDP Socket** | 极低 | 极致低延迟 | 需自己做可靠性 |
| **gRPC** | 中 | 工程化交付 | 企业对接正式接口 |
| **LSL 直连** | 低 | 游戏直接订阅 | Unity 有 LSL4Unity 插件 |

### 6.3 游戏引擎选型

| 引擎 | 优势 | 劣势 | 建议 |
|---|---|---|---|
| **pygame / Python** | 大一最友好，和解码同语言，出原型最快 | 画面弱 | **第一个 Demo 用它** |
| **Web（p5.js / Three.js）** | 零安装、浏览器演示、分享方便 | 3D/性能一般 | 做对外演示很合适 |
| **Unity + LSL4Unity** | 3D 强、康复游戏行业主流、企业认可 | 学习曲线陡 | 第二版升级目标 |
| **Godot** | 免费轻量、上手快于 Unity | 生态较小 | 备选 |

**强烈建议的路线**：`pygame/Web 原型 → 验证闭环 → Unity 正式版`。不要一开始就啃 Unity。

### 6.4 一条极其重要的工程建议：Mock 先行

**先用键盘模拟脑控，把游戏做完。**

```
第 1 步：游戏用键盘 ← → 控制，跑通玩法、画面、反馈、计分
第 2 步：把键盘输入换成"读取一个假数据源的预测结果"（mock decoder）
第 3 步：把 mock 换成"回放离线数据集的分类器输出"
第 4 步：接入真实 LSL 在线流
```

好处：游戏开发和算法开发**完全解耦、可并行**，团队里不搞算法的人也能立刻产出成果；每换一层只改一个接口，问题定位清晰。这是专业工程做法，能帮你们省掉大量联调痛苦。

## 7. 分阶段实施路线（脑控游戏版）

| 阶段 | 周次 | 目标 | 验收 |
|---|---|---|---|
| **G0 游戏原型** | 1–3 | 用键盘控制的完整游戏（pygame/Web） | 能玩、有分数、有反馈 |
| **G1 离线接通** | 4–6 | mock decoder → 离线数据集驱动游戏 | 播放回放数据时游戏正确响应 |
| **G2 真实在线** | 7–10 | LSL 接入 + 校准流程 + 在线分类 | 完成一次完整"校准→游戏"流程 |
| **G3 体验调优** | 11–14 | 平滑、门限、反馈、难度自适应 | 3 名以上同学实测，主观可用 |
| **G4 数据与自适应** | 15–18 | 落盘记录 + 在线微调/迁移 | 跨次使用校准时间下降 |
| **G5 场景升级** | 19–24 | Unity 正式版 / 康复游戏版本 | 可对企业和患者演示 |

> G0 与《规划》中的阶段 0–1（MNE 学习、离线基线）**并行推进**，互不阻塞。

## 8. 评估体系（脑控游戏专用）

准确率不是唯一指标，甚至不是最重要的指标。

### 8.1 技术指标
- 分类准确率 / Kappa
- **端到端延迟**（trial 开始 → 游戏响应）
- **误触发率**（静息时错误触发动作的频率）
- **方向切换频率/抖动率**（衡量"稳定感"）
- ITR（bits/min）

### 8.2 游戏与体验指标
- 任务完成率、平均完成时间、得分
- **脑控感（Sense of Agency）**：用户是否觉得"是我在控制"
- **主观负荷**：NASA-TLX 量表
- **游戏体验**：GEQ（Game Experience Questionnaire）
- **可用性**：SUS 量表

### 8.3 康复场景指标（对齐企业）
- 训练依从性（单次训练时长、主动完成率）
- 患者参与度与情绪变化
- 与康复动作的对应度（想象患侧手 → 真实训练意图）

> 建议第一版就做一份**简版问卷（5–8 题）**，每次用户测试后填写。数据虽少，但能立刻发现"算法指标好但体验差"的问题。

## 9. 康复场景延伸（这是打动翔宇医疗的关键）

翔宇医疗是康复医疗器械企业，纯娱乐游戏对他们的价值有限，**"游戏化康复"才是真正的商业落点**：

- **场景**：脑卒中 / 神经损伤患者的上肢运动功能康复训练；
- **痛点**：传统康复训练枯燥 → 依从性差；患者难以感知"微小的进步"；
- **脑控游戏的价值**：
  1. 把"运动想象训练"包装成游戏，**提升训练依从性**；
  2. 游戏分数/进度**量化康复进展**，可视化给医生和患者；
  3. 训练过程**持续采集脑电数据**，反哺算法与科研；
- **设计注意**：患者疲劳阈值低、伪迹多（可能有运动障碍、痉挛），需要更强的鲁棒性与更宽松的节奏；
- **建议**：G3 之后做一个**"康复版弹球/抓取"演示给企业看**，把"娱乐 Demo"升级为"康复 Demo"，合作黏性会强很多。

## 10. 常见坑清单（照着避）

- [ ] **只盯算法精度**，游戏玩起来依然别扭 → 忽视平滑、门限、反馈设计
- [ ] **没有静息态** → 用户一放松就误触发，体验崩溃
- [ ] **没有 mock 阶段** → 游戏和算法耦合，联调地狱
- [ ] **决策窗口照抄论文**（如 4 s 窗口 + 1 s 步长）→ 延迟太大，游戏没法玩。要按游戏节奏重新定窗口
- [ ] **不做校准流程** → 直接用通用模型，新用户准确率惨不忍睹
- [ ] **单局时间过长** → MI 疲劳，数据质量下降
- [ ] **忽略 BCI illiteracy** → 遇到分不出的用户就束手无策
- [ ] **忘记记录数据** → 后期无法做自适应的数据资产白丢
- [ ] **不测真实延迟** → 演示时说不出延迟数字，企业会质疑
- [ ] **用娱乐游戏直接对患者** → 忽略伦理、安全和适配性
