# 离线 trial 三窗投票 vs 在线稳定化：是否完全一致？

> 结论：**不完全一致。** 目标相同（都为了"宁可迟钝、不可抖动"），但规则不同、时间尺度不同。讲稿/报告不得把两者说成同一件事。
> 日期：2026-11-05；对应问题来源：王释贤审阅提问。

## 一、离线评测口径（报告数字的来源）

代码：`bci-decoder/scripts/m3/itr_report.py` 第 134 行；伪在线脚本同逻辑（`pseudo_online_vs_offline.py` 第 185–186 行）。

- 每个 trial 内切 3 个窗口：起点 `cue+0 / +0.5s / +1.0s`，窗长 2.0 s、步长 0.5 s。
- 汇总规则：**众数（mode）** —— 3 窗里 ≥2 票即定，**不要求全一致**。
- 无概率平滑、无置信度门限、无 idle 回退；一次判完，不做跨 trial 的状态保持。
- 输出的是**评测指标**（trial acc / Kappa / ITR），不是游戏指令。

## 二、在线稳定化（游戏真正消费的）

代码：`bci-decoder/bci_decoder/pipeline/postprocess.py`（`DecisionStabilizer`）；默认参数见 `config.py`：

| 参数 | 默认值 | 作用 |
|---|---|---|
| `vote_window` | 3 | 连续 N 次一致才切换输出 |
| `ema_alpha` | 0.4 | 概率指数平滑，抑制单次抖动 |
| `min_confidence` | 0.6 | 低于此置信度 → 输出 `idle` |

规则：

1. 每来一次分类概率先做 **EMA 平滑**（alpha=0.4）。
2. 平滑后的 top 类进入长度 3 的队列；**只有连续 3 次完全相同**（`len(set(votes))==1`，即 3/3）才算 stable。
3. 不 stable 时**保持上一次输出**（不是输出多数票）。
4. stable 且置信度 ≥0.6 才切到新方向；<0.6 → `idle`。

## 三、差异对照

| 维度 | 离线 trial 3 窗投票 | 在线稳定化 |
|---|---|---|
| 聚合规则 | 众数，2/3 即可 | 连续 3 次全一致，3/3 |
| 概率平滑 | 无 | EMA α=0.4 |
| 置信度门限 | 无 | <0.6 → idle |
| 抖动时 | 直接给多数票 | 保持上一次输出 |
| 跨 trial 状态 | 无 | 有（`_current` 持续保持） |
| 时间尺度 | trial 内 3 窗（覆盖 cue+0 ~ +3.0 s） | 每次决策滑动累加，3 次决策≈1.5 s 才可能切换 |

## 四、对报告/讲稿的表述要求

- 可以说：「评测口径为 **trial 内 3 窗多数投票**」。
- 不能说：「游戏里就是 3 窗投票」——在线实际更严格（3/3 一致 + EMA + 门限）。
- 不能说：「离线 Kappa = 在线体验准确率」——在线稳定化会牺牲响应速度换取稳定，二者不应等号。
- 若被追问「为什么在线更严」：回答——游戏里误切方向的体验代价远大于慢半拍（设计原则写在 `postprocess.py` 文档字符串里）。
