## 1. 项目定位与交付边界

### 1.1 交付边界（先划清，否则会做成"半个游戏 + 半个算法"）

| 分工 | 归属 | 说明 |
|---|---|---|
| 脑电采集硬件 | 企业 / 设备方 | 我们只对接其数据流（优先 LSL） |
| **在线解码模块** | **本项目** | **核心交付物** |
| 游戏画面、玩法、UI | 游戏团队（或我方 1 人兼） | 我们只提供标准输出接口 |
| 游戏与解码的联调 | 双方 | 以接口契约为准 |
| 真实被试采集与伦理 | 企业主导，我方配合 | 涉人数据必须走伦理审查 |

**我们交付的"产品"本质上就是一段消息流**：

```json
{"t_data": 12.345, "t_wall": 8412.551, "label": "left", "label_id": 0,
 "confidence": 0.83, "probs": [0.83, 0.17], "state": "running",
 "compute_ms": 1.2, "window_seconds": 2.0}
```

游戏拿到它就能驱动角色——**这是衡量模块成败的唯一标准**。

### 1.2 为什么选"脑控游戏"而不是"脑控轮椅"作为第一版载体

| 对比维度 | 脑控轮椅 | **脑控游戏** |
|---|---|---|
| 容错要求 | 极严（安全责任） | 宽松（错了重来） |
| 决策窗口 | 越短越好 | 可设计成 1–3 s |
| 精度门槛 | >90% 才敢用 | 70% 就能"玩起来" |
| 数据回流 | 少 | **多（持续产生标注数据）** |
| 演示效果 | 风险高 | **视觉冲击强、易做 Demo** |
| 康复契合度 | 一般 | **极高（游戏化康复）** |

**策略**：用游戏打磨在线解码闭环、把数据攒起来，再把**同一套解码模块**复用到轮椅/康复场景。这与企业"最终形成可调用的在线解码模块"的目标完全一致。

### 1.3 大一团队的成功标准（写进验收）

> - 公开数据集上，二分类运动想象达到**可复现的真实基线**（说明方法有效）；
> - 伪在线回放中，端到端响应可测量、计算耗时 p95 < 50 ms（说明可落地）；
> - 跨被试精度下降**可量化、可解释**（说明有泛化能力）；
> - **不使用任何合成数据对外报告准确率**（学术诚信红线）。

## 2. `bci-decoder/` 链路：团队已有实现与已验证的技术结论

### 2.1 `bci-decoder/` 是什么

`bci-decoder/` 是**本团队成果**（团队借助 AI 编码助手实现，2026-10-15 拍板、计入项目进度）；开工前原文称它为"他人编写的示例程序"，该表述已作废。它的作用有两个：

1. **照着学**：看清一条完整链路长什么样，少走弯路；
2. **验证可行性**：跑一遍，确认这条路在技术上走得通。

它有下面这些部件（**我们要理解它，然后自己动手实现自己的版本**）：

> 骨架 = 管道；MVP = 管道 + **游戏**。本节只说明"参考实现长什么样"，**我们的项目尚未开始**。

```
bci-decoder/
├── bci_decoder/
│   ├── sources/       # 数据源：mock(自检) / replay(离线回放) / lsl(真实设备)
│   ├── buffer.py      # 环形缓冲（固定容量，保证长跑内存恒定）
│   ├── pipeline/      # preprocess(因果滤波+CAR+伪迹) → features → classifier → postprocess
│   ├── outputs/       # 输出通道：console / jsonl / websocket
│   ├── core.py        # 解码引擎：串起"源→缓冲→流水线→输出"
│   ├── config.py      # 全部参数集中在一个 YAML
│   └── cli.py         # 命令行入口 run / benchmark / show-config
├── configs/           # default / demo_online / demo_replay
├── scripts/           # bootstrap_demo.py 端到端自检与训练
└── tests/             # 单元测试 + 端到端测试
```

**关键设计（我们要在自己实现里沿用这些思路）**：

1. **数据源可替换**——实现 `Source.stream()` 即可接入任意设备，这是"即插即用"的关键；
2. **流水线各环节独立可测**——便于定位问题；
3. **输出多通道**——同一次解码可同时送终端、落盘、WebSocket；
4. **配置驱动**——交付时企业只改一个 YAML。

### 2.2 已验证出的技术结论（**合成数据自检，不是算法成绩**）

> ⚠️ 下表数字来自**本团队链路 `bci-decoder/` + 合成数据**。列在这里只为说明"技术可行、量级可控"，
> **它们不是算法成绩，不能当作准确率对外报告**。真实数字要等里程碑 ③ 用公开数据集（BCI IV 2a）实测。

| 项目 | 实测结果（合成数据，2026-10-15 核实） | 命令 |

| 端到端响应估算 p95 | ≈ 2002 ms（= 2 s 窗口 + 2.1 ms 计算） | 同上 |

> **两条纪律**：
> ① 合成数据的数字**只用于说明可行性**，**绝不作为团队成绩对外报告**；
> ② 我们自己的准确率必须等 ③ 中期评审用 `moabb` + BCI IV 2a 测出来，**在此之前不报任何准确率**。

### 2.3 由此得到本项目最重要的一个技术结论

> **延迟瓶颈不在算法，而在窗口长度。**
> 计算只占 2.1 ms（0.10%），窗口累积占 2000 ms（99.90%）。
> 把 LDA 换成深度网络、上 GPU，对端到端延迟**几乎没有任何帮助**；
> 真正有效的手段是**缩短窗口**——但窗口越短，可用信息越少，准确率越低。

因此，**"窗口长度"是本项目最核心的工程决策**，必须与游戏团队共同确定：

| 游戏类型 | 可接受响应 | 建议窗口 | 后果 |
|---|---|---|---|
| 回合制 / 迷宫 / 弹球 | 2–3 s | **2.0 s** | 准确率优先（**MVP 采用**） |
| 弹球 / 赛车 | 1–1.5 s | 1.0 s | 需重新训练模型 |
| 实时动作 | < 0.5 s | — | 运动想象范式**不适合** |

**给企业的建议**：不要在需求上既要"高准确率"又要"极低延迟"，这在物理上冲突。正确做法是**先定游戏节奏，再倒推窗口长度，最后在窗口内优化准确率**。

## 3. 难度控制：三层策略（针对"团队全是大一"的核心设计）

大一学生最大的风险不是不努力，而是**选错难度**。本计划把全部工作分成三层：

| 层级 | 内容 | 是否 MVP 必做 | 难度 | 当前状态 |
|---|---|---|---|---|
| **第一层：工程闭环** | 解码链路 + 单测 + 压测 + **游戏 Demo** + Docker + 文档 | **必做** | ★ | 🔄 **进行中**：链路 + 单测 ✅（14/14）；压测 / 游戏 / Docker ⏳ 未开始 |
| **第二层：真实数据基线** | `moabb` 拉公开数据集 + `pyRiemann` 跑二分类 | **必做** | ★★ | ⏳ 未开始 |
| **第三层：研究性探索** | 跨被试迁移、多脑区融合、深度模型 | ⚠️ **时间允许才做** | ★★★★ | ⏳ 未开始 |

### 3.1 明确"本版不做"的清单（写下来才好拒绝）

- ❌ **不做 4 分类**——第一版只做 **2 类（左手 / 右手）+ 静息/idle**；
- ❌ **不做深度模型**——EEGNet 等在跨被试上经常打不过 CSP+LDA / 黎曼方法，且数据量不够；
- ❌ **不做真实患者采集**——伦理与合规成本过高，本版只用公开数据 + 健康同学自测；
- ❌ **不做 Unity 正式版**——先用 pygame/Web 出原型；
- ❌ **不做在线自适应微调**——列为下一期方向；
- ❌ **不自己写算法库**——CSP、黎曼、评测框架全部复用开源实现。

### 3.2 给大一团队的"反坑"约定（团队纪律）

| 坑 | 本项目约定 |
|---|---|
| 只做离线，交付时答不上"能实时跑吗" | 从第一天起，**所有实验都用因果滤波**；延迟列为考核指标 |
| 一上来就上深度学习 | **先传统后深度**；用传统基线证明深度确实更强才换 |

### 4.1 复用纪律（避坑）

- **评测纪律**：`moabb` 是唯一对外报准确率的来源；`mock`/`synth` 只用于验证"链路通不通"。
- **在线 vs 离线**：不要照抄离线教程的零相位 `filtfilt`（用到未来样本，在线不可用）。
- **通道顺序**：接真设备时通道顺序必须与采集端一致，否则 C3/C4 侧向颠倒，模型会**稳定地输出相反结果**——这是最难排查的错误。
- **许可**：商用前逐个确认 License；若未来静态链接 GPL 系项目需重新评估。

## 5. 技术方案（MVP 版）

### 5.1 主链路

```
原始 EEG ─▶ 因果滤波 ─▶ CAR重参考 ─▶ 伪迹标记 ─▶ 环形缓冲
                                                     │
                                          滑窗(2s/步长0.5s)
                                                     ▼
                                    频带功率特征 ─▶ LDA ─▶ 决策稳定化 ─▶ 输出
```

| 环节 | MVP 选择 | 理由 |
|---|---|---|
| 工频 | 50 Hz 陷波（IIR, Q=30），因果带状态 | 中国工频 |
| 带通 | 8–30 Hz（mu + beta） | 运动想象主频段 |
| 重参考 | 共平均参考 CAR | 无状态、简单有效 |
| 伪迹 | 峰峰值阈值，**只标记不丢弃** | 丢弃会造成输出中断，体验更差；标记后降级为 `idle` 更符合直觉 |
| 特征 | **频带功率对数**（mu/beta × 8 通道 = 16 维） | 快、可解释、数据需求低 |
| 分类器 | **LDA**（标准化 + 线性判别） | 小数据、低延迟的强基线 |
| 后处理 | **EMA 平滑 + 连续 3 次一致性投票 + 置信度门限** | **宁可迟钝，不可抖动** |

### 5.2 通道布局（已为多脑区融合预留）

`C3, Cz, C4, CP3, CP4, P3, P4, Oz`，天然包含：

- **运动区**（C3/Cz/C4/CP3/CP4）：运动想象主战场；
- **枕叶**（Oz/P3/P4）：alpha 节律与注意状态；
- **前额叶**（需额外加 F3/F4/Fz）：认知负荷、注意——**下一期**。

融合方法按复杂度递增：① 特征级拼接（先做这个）→ ② 分区独立分类 + 决策融合 → ③ 多分支网络 + 区域注意力（研究向）。
**必须做消融实验**：单区 vs 多区。**没有增益也是有效结论**，它能避免后续投入浪费。

### 5.3 状态机（防止"用未校准模型驱动游戏"）

```
   ┌────────┐  start   ┌──────────────┐  校准完成   ┌─────────┐
   │  IDLE  │─────────▶│ CALIBRATING  │────────────▶│ RUNNING │
   └────────┘          └──────────────┘             └────┬────┘
        ▲                                               │
        │                  stop / 信号质量持续异常       │
        └───────────────────────────────────────────────┘
                              │
                              ▼
                        ┌───────────┐
                        │  ERROR    │  设备断开 / 数据超时
                        └───────────┘
```

| 状态 | 行为 | 输出 |
|---|---|---|
| `IDLE` | 不推理 | 不发消息 |
| `CALIBRATING` | 采集校准数据、训练/微调模型 | 只发进度 |
| `RUNNING` | 正常解码 | 发 `label` / `idle` |
| `ERROR` | 停止推理、告警 | 发错误状态 |

5. **深度学习**：**本版不要求**，时间充裕再跑 Braindecode 示例。

推荐资源：《脑机接口导论》、MNE-Python 官方文档、MOABB benchmark 文档、[`NeuroTechX/awesome-bci`](https://github.com/NeuroTechX/awesome-bci)。

### 9.3 成本预算（体现"低成本"）

| 项目 | 预算 | 说明 |
|---|---|---|
| 软件 / 框架 | **￥0** | NumPy、SciPy、scikit-learn、MNE、MOABB、pyRiemann 全部开源免费 |
| 公开数据集 | **￥0** | BCI IV 2a/2b、OpenBMI、PhysioNet 均可免费获取（`moabb` 自动下载） |
| 计算资源 | **￥0** | 普通笔记本即可（现有自检计算 p95 ≈ 2 ms，**无需 GPU**） |
| 脑电采集设备 | **￥0** | MVP 阶段借用企业设备；如需自备，OpenBCI Cyton 约 ￥5–8k，**本版不采购** |
| 云服务 / 服务器 | **￥0** | Windows 笔记本本地运行即可，不联网也可演示 |
| **合计** | **￥0（硬件由企业提供）** | |

> **成本控制的核心逻辑**：不买硬件、不租算力、不用付费软件。全部成本转化为**人力时间**。

## 11. 需要与企业确认的 5 个问题（① 立项与 MVP 规格 · 10/13 前必办）

1. **设备**：现有采集设备的**型号、通道数、采样率、通道顺序**？是否有 SDK / LSL 支持？
2. **任务**：期望**类别数**（2 类还是 4 类）？单次决策允许的最长响应时间是多少？
3. **接口**：脑控游戏当前需要什么格式的输出（WebSocket / LSL / 串口 / 定制 SDK）？
4. **数据**：是否已有企业侧实测数据可共享（**哪怕少量也比公开数据更有说服力**）？
5. **验收**：验收标准由谁定义、以什么数据为准、什么时候验收？

> 第 1 题的"通道顺序"必须拿到**书面确认**——顺序错了会导致模型稳定输出相反结果。

## 附录 A：接口契约摘要

**输入（脑电数据流）**

| 项 | 约定 |
|---|---|
| 数据格式 | `(n_channels, n_samples)`，单位 µV |
| 推荐通道 | `C3, Cz, C4, CP3, CP4, P3, P4, Oz` |
| 采样率 | 250 Hz（可配置） |
| 推荐接入 | LSL 流，名称可配置 |
| 数据块 | 建议 100 ms 一块 |

**输出（解码结果）** 见 1.1 节 JSON 示例。

**控制消息（建议后续扩展）**

```json
{"cmd": "start"}
{"cmd": "stop"}
{"cmd": "calibrate", "seconds": 120}
{"cmd": "load_subject", "id": "sub01"}
```

## 附录 B：切换到真实设备的操作步骤

1. 确认设备能发布 **LSL 流**（多数采集软件都有该选项）；
2. `pip install pylsl`；
3. 修改配置：

```yaml
source:
  kind: lsl
  stream_name: "你的设备流名称"
  ch_names: [与设备实际通道顺序完全一致的通道名]   # 顺序必须完全一致
  sfreq: 250.0
```

4. 先用 `console` 输出观察 1 分钟，确认信号质量与时间戳正常；
5. 再切到 `websocket` 与游戏联调。

## 附录 C：兼容性与成本友好性说明（回应"兼容性强、成本低"）

| 兼容性维度 | 做法 |
|---|---|
| **设备兼容** | 只要设备能发 LSL 即可接入；无 LSL 时按 `Source` 接口写适配器（约 50 行） |
| **游戏引擎兼容** | 输出 WebSocket/JSON，语言无关；Unity 用 `LSL4Unity`，Web/pygame 直接连 |
| **操作系统兼容** | 纯 Python + 开源库，Windows / Linux / macOS 均可 |
| **硬件门槛** | 无 GPU 要求（现有自检计算 p95 ≈ 2 ms） |
| **参数兼容** | 全部参数集中在单个 YAML，企业只改一个文件 |
| **模型可替换** | 分类器统一 `predict_proba` 接口，换 LDA → 黎曼 → ONNX 深度模型不改引擎 |
